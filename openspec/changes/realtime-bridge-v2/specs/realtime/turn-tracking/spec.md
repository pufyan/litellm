## Purpose

Корректное отслеживание хода разговора независимо от того, как конкретная модель сигнализирует границы: одиночный ответ, реплики со статусом взаимодействия или поток без границ ответов.

## ADDED Requirements

### Requirement: Состояния хода
Ход находится в одном из состояний `LISTENING`, `SPEAKING`, `WORKING`, `IDLE`. Сигнал завершения берётся из дескриптора: `response.done`/`turnComplete` для `single-response`, `interaction_status == IDLE` для `utterance-plus-status`, границы из транскриптов и плеера для `no-response-boundary`.

#### Scenario: Extended Thinking с промежуточным филлером
- **WHEN** модель прислала `turnComplete: true` при `interaction_status == IN_PROGRESS`
- **THEN** ход остаётся в `WORKING`, интерфейс не возвращается в listening, следующая реплика относится к тому же ходу

#### Scenario: GPT-Live без границ ответов
- **WHEN** идёт поток транскриптов и аудио без события конца ответа
- **THEN** мост выделяет границы реплик для клиентского диалекта и spend-лога, не теряя и не дублируя текст

### Requirement: Закрытие оборванного хода
При уходе хода в прошлое из-за reconnect оборванный ответ закрывается явно (событие завершения клиенту, сброс состояния хода), висящих незавершённых ответов не остаётся.

#### Scenario: Обрыв посреди речи модели
- **WHEN** соединение с бэкендом упало, пока модель говорила
- **THEN** клиент получает закрывающее событие для начатого ответа, новый ход начинается с чистого состояния

### Requirement: Идемпотентность границ хода
Границы идентифицируются ключом response_id (настоящий или synthetic `bridge-<uuid>`). Повторное закрытие того же ключа дропается с логом; дубли дельт транскрипта отсекаются по (`start_ms`, `end_ms`, `delta`); дельты, пришедшие после закрытия, пишутся в лог транскрипта без переоткрытия хода. Речь бэкенда при состоянии `LISTENING` переводит трекер в `SPEAKING` с синтетическим `response.created`.

#### Scenario: Поздний настоящий done
- **WHEN** ход уже закрыт синтетическим событием при reconnect, затем приходит настоящий `response.done` с тем же response_id
- **THEN** второй close дропается, клиент видит ровно одно завершение
