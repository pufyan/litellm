## Purpose

Обрыв соединения — штатное событие (goAway каждые ~10 минут, лимиты длительности), а не авария. Продолжение сессии идёт по лестнице от дешёвого нативного механизма к дорогому, зацикливание исключено политикой, а не надеждой.

## ADDED Requirements

### Requirement: Лестница продолжения
Мост пробует механизмы строго по порядку: нативный resume-handle провайдера → fork stored-сессии (где поддерживается) → сидирование истории при старте штатным механизмом провайдера → реплей транскрипта в свежую сессию. Переход на следующую ступень — только после исчерпания предыдущей. Ступень, чьи предусловия не выполнены в рантайме (`store: false`, ZDR-проект, отказ провайдера), пропускается как недоступная без повторов, а не считается исчерпанной попытками.

#### Scenario: Плановый goAway у Gemini
- **WHEN** провайдер прислал goAway с запасом времени
- **THEN** мост переподключается с последним resumption-handle до истечения времени, звонок продолжается без потери контекста

#### Scenario: Исчерпан нативный resume
- **WHEN** resume одним handle N раз подряд закончился обрывом
- **THEN** мост открывает свежую сессию с сидированной историей, а не продолжает долбиться тем же handle

### Requirement: Политика reconnect без зацикливания
Учитываются только reconnect, после которых был реальный обмен (голос или подтвержденный setup плюс живой трафик дольше порога). Служебные кадры вроде `setupComplete` счётчик не сбрасывают. После лимита — эскалация по лестнице, затем вежливое завершение с reason, а не бесконечный цикл.

#### Scenario: Повторяющийся 1011
- **WHEN** каждое переподключение с тем же handle закрывается провайдером
- **THEN** после N попыток мост уходит на свежую сессию; звонок не висит в вечном reconnect

### Requirement: Один владелец reconnect
Reconnect выполняется только через writer; concurrent-запросы коалесцируются в один. Два бэкенд-сокета на одну сессию не открываются. Коалесцирование — через generation counter: опоздавший запрос присоединяется к in-flight попытке. Close wins: переход `RECONNECTING→CLOSING` разрешён с абортом dial и закрытием полуоткрытого сокета; запросы reconnect в `CLOSING` игнорируются. Общий бюджет reconnect ограничен попытками и таймаутом; после исчерпания — graceful close с явной ошибкой клиенту, висеть в `RECONNECTING` запрещено.

#### Scenario: Одновременный обрыв и session.update
- **WHEN** обрыв бэкенда совпал с клиентским `session.update` после setup
- **THEN** выполняется ровно один reconnect, второй сокет не открывается и не теряется

#### Scenario: SIGTERM посреди reconnect
- **WHEN** бэкенд-нога в `RECONNECTING`, пришёл сигнал остановки
- **THEN** dial абортится, полуоткрытый сокет закрывается, сессия идёт по graceful close

### Requirement: Обновление credentials при reconnect
Если дескриптор требует обновления токена, заголовки пересобираются перед каждой попыткой reconnect, а не переиспользуются стартовые. Провал обновления (включая 1 ретрай) ведёт к эскалации по лестнице, а не к вечному ожиданию.

#### Scenario: Reconnect после истечения токена
- **WHEN** с момента старта сессии прошло больше времени жизни токена
- **THEN** reconnect уходит со свежим токеном и не получает 401
