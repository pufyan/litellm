## Purpose

Мост клиент ↔ провайдер с предсказуемым жизненным циклом сессии: порядок кадров гарантирован, переустановление одной ноги не трогает другую, остановка всегда вежливая и подтверждённая. Основа, на которую ложатся остальные capability этого ченджа.

## ADDED Requirements

### Requirement: Две независимые ноги с явными состояниями
Каждая нога (клиентская, бэкенд) имеет именованное состояние из набора `CONNECTING`, `AWAIT_SETUP`, `LIVE`, `RECONNECTING`, `CLOSING`, `CLOSED`. Переходы выполняются только через объявленные переходы; комбинация «восемь независимых флагов» недопустима.

#### Scenario: Обрыв бэкенда не трогает клиентскую ногу
- **WHEN** бэкенд-сокет закрыт провайдером посреди `LIVE`
- **THEN** бэкенд-нога переходит в `RECONNECTING`, клиентская остаётся в `LIVE`, клиент не получает событие закрытия

### Requirement: Один writer в бэкенд
Все кадры в бэкенд отправляются только через очередь, которую разбирает единственная задача-писатель. Порядок отправки равен порядку постановки в очередь.

#### Scenario: Живые кадры не обгоняют досылаемые
- **WHEN** после reconnect досылается буфер и одновременно приходят живые аудиокадры клиента
- **THEN** провайдер получает сначала весь буфер, затем живые кадры, в исходном порядке

### Requirement: Две линии очереди
Управляющие сообщения (`session.update`, `response.create`, закрытие) идут линией управления, аудио — линией данных. Досылка аудио не блокирует чтение ответов провайдера и отправку управления.

#### Scenario: Ответ модели идёт во время досылки
- **WHEN** досылается полный буфер (~200 кадров)
- **THEN** ответы провайдера продолжают читаться и пересылаться клиенту без паузы в секунды

### Requirement: Graceful close с подтверждением
Остановка сессии — протокол: зарегистрировать ожидание финального события, отправить close, дождаться финального события с usage и reason, затем освободить транспорт. Если транспорт упал раньше финала — зафиксировать «finalization unconfirmed». Механика handshake — здесь; содержимое и формат usage — за `realtime/voice-billing`.

#### Scenario: Штатное завершение звонка
- **WHEN** клиент закрыл сокет после разговора
- **THEN** бэкенд-сессия закрыта вежливо, финальный usage записан в spend-лог, висящих сокетов не осталось

### Requirement: Таймауты сессии
Сессия имеет таймаут простоя и максимальную длительность. Срабатывание таймаута ведёт по протоколу graceful close с соответствующим reason.

#### Scenario: Зависший клиент
- **WHEN** от клиента нет кадров дольше таймаута простоя
- **THEN** сессия закрывается вежливо, сокет провайдера освобождается без ожидания закрытия со стороны провайдера

### Requirement: Guardrails как подписчик
Проверки контента выполняются конкурентным подписчиком на поток транскриптов с явным состоянием блокировки в коде приложения. Блокировка действий и управление воспроизведением — механизм; инструкция модели — только следствие.

#### Scenario: Срабатывание проверки посреди речи
- **WHEN** проверка отклонила запрос пользователя, пока модель говорит
- **THEN** затронутые действия заблокированы в состоянии приложения, воспроизведение остановлено на стороне плеера/релея, модели отправлена корректирующая инструкция

### Requirement: Надзор за writer и границы очередей
Смерть задачи writer ведёт к fail-fast закрытию сессии с reason, а не к молчаливому росту очереди. Audio-линия ограничена капами; при переполнении чтение клиента приостанавливается (backpressure), дропы считаются и логируются. Control-линия обслуживается строго первой; pacing применяется только к аудио. Некорректный JSON кадра дропается со счётчиком, читающий цикл продолжает работу.

#### Scenario: Упавший writer
- **WHEN** задача writer завершилась с исключением при живой сессии
- **THEN** сессия закрывается вежливо с reason, очередь не растёт молча

#### Scenario: Переполнение аудио-линии
- **WHEN** бэкенд в `RECONNECTING`, клиент продолжает слать аудио сверх капа
- **THEN** чтение клиента приостановлено, превышение посчитано в лог, порядок ранее принятых кадров сохранён

### Requirement: Совместимость клиентского диалекта
Клиенты `/v1/realtime` продолжают получать диалект OpenAI Realtime (`session.created/updated`, `response.created/done`, `conversation.item.*`) независимо от бэкенда. Gen2-события бэкенда транслируются адаптером.

#### Scenario: Старый voip-клиент на новом бэкенде
- **WHEN** за мостом модель без события конца ответа (например GPT-Live)
- **THEN** клиент всё равно получает завершённый `response.done` для каждого ответа
