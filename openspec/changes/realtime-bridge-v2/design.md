## Context

См. `proposal.md` — Why. Текущее состояние: `RealTimeStreaming` (2271 строка, ~35 изменяемых полей, две пишущие задачи), диспетчер провайдеров на if/elif в `realtime_api/main.py`, Bedrock (`llms/bedrock/realtime/`) и Vertex/STT (`llms/vertex_ai/realtime/`, `audio_transcription/realtime_*`) на собственных мостах, spend-лог только токенный. Ограничения: каждая realtime-правка проверяется живым звонком через прокси с `LITELLM_LOG=DEBUG`; Gemini принимает один setup на соединение; pacing аудио 20 мс под серверный VAD; fork stored-сессий требует `store: true` и non-ZDR. Источники требований Gen2: `developers.openai.com/api/docs/guides/live*`, `ai.google.dev/gemini-api/docs/live-api/thinking`, `.../live-api/session-management`.

Целевой каркас:

```
client ws (/v1/realtime, диалект OpenAI Realtime — неизменен)
   |
SessionBridge
   |-- leg(client): состояния, таймауты, graceful close
   |-- leg(backend): состояния, reconnect только через writer
   |-- writer: очередь x2 линии (control / audio), единственный отправитель
   |-- turn tracker: LISTENING/SPEAKING/WORKING/IDLE + плагин завершения
   |-- guardrails: конкурентный подписчик транскриптов, явное состояние блокировки
   |-- billing: токены | секунды голоса + бэкенд по delegation_id
   |
provider adapter (канон <-> протокол) + capability-дескриптор из реестра
   |
backend ws (gen1: realtime-диалекты / gen2: /v1/live, BidiGenerateContent)
```

## Goals / Non-Goals

**Goals:**
- Предсказуемый жизненный цикл сессии для всех провайдеров Gen1 и Gen2.
- Новые модели заводятся дескриптором + адаптером, без правок ядра.
- Деньги корректны для посекундного и токенного биллинга.
- Каждая фаза идёт strangler-ом поверх работающего моста, с живым звонком.

**Non-Goals:**
- Переезд Bedrock (`llms/bedrock/realtime/`) и Vertex/STT-мостов на общий мост — отдельный чендж-продолжение.
- Клиентский `/v1/live`-passthrough для внешних клиентов — не в этом чендже.
- Полный пайплайн-фреймворк в духе Pipecat — заимствуем приёмы (типы, очереди, состояния), не каркас.
- Унификация `SSL_VERIFY` и чистка мёртвого кода — отдельные точечные ченджи.

## Principles

Что должно быть:
- Ноги независимы: переустановление одной не меняет состояние другой (B2BUA).
- В бэкенд пишет ровно один writer; порядок = порядок очереди.
- Событие разбирается один раз в типизированный объект и дальше travels typed.
- Состояния именованные, с объявленными переходами; новый булев флаг — только через пересмотр машины.
- Предпочитать нативный механизм провайдера (resume-handle, fork, `session.input`) собственному; свой реплей — последняя ступень.
- Решения выводятся из capability-дескриптора, а не из ветвлений по имени модели.
- Guardrail блокирует в коде приложения и управляет воспроизведением; инструкция модели — следствие, а не механизм блокировки.
- Spend-лог: лучше `unconfirmed`, чем молчаливый ноль.

Чего не должно быть:
- Двух писателей в один сокет; flush, блокирующего чтение; reconnect вне writer.
- `turnComplete` как синонима «дело сделано» — только через плагин завершения.
- Буферизации без границ (кап по сообщениям и байтам; лимит ходов).
- Трактовки тишины транскриптов как тишины звонка (таймауты по аудио-активности и playback, не по событиям).
- Секретов и credentials в транслируемых в модель контекстах.

Ориентиры: Pipecat (типизированные фреймы, две линии очередей), LiveKit AgentSession (именованные состояния, пороги вместо бинарных решений), SIP/B2BUA (независимые ноги, session timers, graceful close с reason), Twilio-минималист (не строить логику там, где провайдер уже умеет).

## Decisions

- **Strangler вместо big-bang.** Почему: поведение голоса (pacing 20 мс, порядок toolResponse, синтетические session-события) видно только живым звонком; большой дифф не бисектится. Альтернатива (переписать мост целиком) отвергнута.
- **Канонические события внутри, диалекты по краям.** Почему: клиентский `/v1/realtime` frozen, провайдеров семь плюс Gen2; N×M трансляций заменяется N+M адаптерами. Альтернатива (прокидывать провайдерские события сквозняком) ломает совместимость клиентов.
- **Дескриптор как данные, не код.** Почему: добавление модели без релиза ядра; таблица ревьюится глазами. Альтернатива (классы-стратегии на провайдера) оставлена для адаптеров трансляции, но не для решений.
- **Лестница продолжения вместо одного resume.** Почему: провайдеры сами дают handle/fork/seed; наш реплей самый дорогой и неточный. Порядок: handle → fork → seed → replay.
- **Биллинг секунд как отдельный путь, не флаг в токенном.** Почему: разные юниты, разные источники, разная сверка с инвойсом; смешивание даст неверные деньги молча.
- **Guardrails подписчиком, не инлайном.** Почему: инлайн в клиентском цикле блокирует чтение и плодит флаги (`_guardrail_turn_detection_update_sent` и friends); конкурентный чек с явным состоянием — по шаблону OpenAI.
- **D7 Аккумуляция usage сквозная (H1).** Почему: провайдер биллит каждую ногу отдельно, инвойс = сумма; сброс на ступени даёт недосчёт. Per-leg max (монотонность против повторов), total = сумма финалов, дедуп бэкенда по (`delegation_id`, `response_id`), unconfirmed-ноги финализируются таймаутом. Альтернатива (доверять последнему снапшоту провайдера за «всю сессию») отвергнута — провайдер видит только свою ногу.
- **D8 Writer под надзором (H2).** Почему: единственный писатель без watchdog — single point of silent failure. Смерть writer → fail-fast close с reason; audio-линия bounded с backpressure на чтение клиента (пауза reads, не молчаливый drop); control — strict priority; pacing только на аудио; битый JSON — drop кадра со счётчиком. Альтернатива (unbounded + drop-oldest молча) отвергнута — теряется голос без следа.
- **D9 Close wins (H3).** Почему: остановка важнее восстановления; два сокета и вис в `RECONNECTING` — худшие исходы. `RECONNECTING→CLOSING` разрешён с абортом dial, `CLOSING→RECONNECTING` запрещён, коалесцирование через generation counter, refresh токена с 1 ретраем затем эскалация, общий бюджет reconnect с явной ошибкой клиенту в конце. Альтернатива (reconnect всегда побеждает) отвергнута — drain при SIGTERM станет негарантированным.
- **D10 Идемпотентные границы (H4).** Почему: сеть дублирует и запаздывает, клиентский стейт хрупок. Ключ — response_id (настоящий или synthetic `bridge-<uuid>`), повторный close — drop+log, дедуп дельт по (`start_ms`, `end_ms`, `delta`), неожиданная речь при `LISTENING` — авто-`SPEAKING` с синтетическим `response.created` (бэкенд побеждает). Альтернатива (доверять порядку событий) отвергнута — порядок после reconnect не гарантирован провайдером.

## Risks / Trade-offs

- [Risk] Регрессия голоса, невидимая юнит-тестам → Mitigation: правило «звонок до коммита» на каждую фазу + юнит-тесты на порядок отправки writer перед рефакторингом.
- [Risk] Gemini отклоняет второй setup на соединении → Mitigation: модель setup `once` в дескрипторе; `session.update` после контента дропается с debug-логом, как сейчас.
- [Risk] Pacing досылки (20 мс) в writer-архитектуре → Mitigation: pacing — свойство линии аудио writer, не клиентского цикла; значение калибруется звонком.
- [Risk] Fork требует `store: true`, проектный флаг и non-ZDR → Mitigation: capability `fork` включается только при выполненных предусловиях, иначе ступень пропускается.
- [Risk] Транскрипт-реплей дорожает с длиной звонка → Mitigation: кап записей + сидирование историей вместо полного реплея где поддерживается.
- [Risk] Двойной учёт (голос + бэкенд) разойдётся с инвойсом → Mitigation: сверка по staging-звонкам с реальными инвойсами перед включением.

## Migration Plan

1. Фаза 0: юнит-сетка на текущее поведение (порядок отправки, границы ходов Gen1) — фиксация baseline.
2. Фаза 1: типы дескриптора + реестр, диспетчер поверх if/elif (поведение не меняется).
3. Фаза 2: writer с двумя линиями; reconnect через writer; удаление прямых send.
4. Фаза 3 (задачи 2.3–2.5): машины состояний ног, фиксированный набор `CONNECTING/AWAIT_SETUP/LIVE/RECONNECTING/CLOSING/CLOSED` (переходы только объявленные; запрещённые пары — например `CLOSING→RECONNECTING` — не выполняются); graceful close; таймауты; drain по новому протоколу.
5. Фаза 4: turn tracker с плагинами завершения Gen1; адаптеры транслируют как раньше.
6. Фаза 5: Gen2-адаптеры (GPT-Live, Gemini 3.8 incl. thinking) + лестница продолжения.
7. Фаза 6: посекундный биллинг + сверка с инвойсами.
8. Фаза 7 (отдельный чендж): Bedrock и Vertex live на общий мост.
- Rollback фаз 1–4: предыдущий коммит моста; клиентский диалект и схемы spend-записей не меняются, откат невидим клиентам. Начиная с фазы 5 (новые поля spend, fork/записи) откат требует отдельного разбора совместимости схем — см. риски.
- Соответствие фаз задачам: Фаза 0 → 1.1, 1.4, 1.5; Фаза 1 → 1.2, 1.3; Фаза 2 → 2.1, 2.2; Фаза 3 → 2.3–2.5; Фаза 4 → 3.1–3.5; Фаза 5 → 4.1–4.5; Фаза 6 → 5.1, 5.2; Фаза 7 → отдельный чендж; финал → 5.3.

## Open Questions

- Значения по умолчанию таймаутов (idle, max-duration): предлагается idle 5 мин / max 2 ч с конфигурированием через `request_data`, финальные цифры — по наблюдению staging. Не меняет спеки и разбивку задач.
- Нужен ли клиентский `/v1/live`-passthrough в принципе: вынесено за скоуп ченджа (см. Non-Goals), решает продукт отдельно.
