## Context

См. `proposal.md`. Текущее состояние по итогам исследования: `RealTimeStreaming` (2283 строки) держит `messages`, `input_messages`, `tool_calls` без капов, чанки транскриптов флашатся только на `response.done`, pending-буфер обходится преппендом при ошибке flush, `RealtimeSessionRegistry` держит сильные ссылки с drain до 600 с, retry-цикл reconnect может терять промежуточные сокеты, `xai _content_part_by_key` растет без evict (у Gemini рядом LRU на 256), Chirp-бэкенд копит `_RecognizeStream` в `_turn`. Капы `200 / 10 МБ / 200 записей` покрывают только часть накопителей.

## Goals / Non-Goals

**Goals:**
- Плоский RSS на часовых звонках и висящих сессиях.
- Каждый накопитель с владельцем и капом, предсказуемая дроп-политика.
- Детерминированное освобождение сокетов, задач, стримов.
- Наблюдаемость без внешних профайлеров в проде.

**Non-Goals:**
- Writer-очередь, ноги с явными состояниями, turn-tracker — это чендж `realtime-bridge-v2`, здесь только границы поверх текущего кода.
- Смена транспорта (Rust, LiveKit-сервер, Pipecat-рантайм) — не в этом чендже.
- Изменение клиентского диалекта и формата spend-записей.

## Decisions

### D1: Ring-buffer с дропом старых и счетчиком
Почему: звонок должен продолжаться при переполнении, оператор должен видеть факт дропа в логе. Альтернатива (бэкпрешер с остановкой чтения) отложена до writer-очереди.

### D2: Кап по двум осям — штуки и байты
Почему: одно аудио-событие и один текстовый чанк различаются на порядки, кап только по штукам пропускает всплеск base64. Байты считаются по длине сериализованного JSON события (`len(json.dumps(evt))`), подсчет только в момент вставки.

### D3: Weak-реестр вместо сильных ссылок
Почему: реестр — наблюдатель для shutdown, а не владелец сессии. Владение остается у задач насоса. Альтернатива (ручной `unregister` на всех путях) уже доказала неполноту потерей задач до `finally`.

### D4: Закрытие сокета в retry-цикле через try/finally на итерацию
Почему: промежуточный сокет виден только внутри итерации, finally на итерацию — единственное место, покрывающее все выходы. Альтернатива (закрытие только в конце цикла) теряет сокеты при `continue`.

### D5: Evict по образцу существующего LRU Gemini
Почему: в кодовой базе уже есть принятый паттерн (`_TOOL_CALL_ID_TO_NAME_MAX=256`), копируем его в xAI и аналогичные словари вместо нового механизма.

### D6: Наблюдаемость через счетчики, не через внешний скрейп в проде
Почему: `tracemalloc`/`objgraph` — процедура staging-проверки, в проде только дешевые счетчики размеров и дропов в debug-лог.

### D7: Spend-критичное не дропается
Почему: `log_messages()` диспатчит именно `messages`, усечение хвоста дает недобиллинг. Кап режет только служебные события (аудио-дельты, ping, промежуточные статусы), spend-критичные (`response.done`, `conversation.item.*completed`, usage, tool-calls) имеют приоритет удержания и отдельный компактный лимит. Паритет spend проверяется дифф-тестом до/после капа.

### D8: Реестр остается сильным, освобождение — детерминированное
Почему: перевод на weak собирает живые сессии на путях потери задачи до `finally` (сокет открыт, насос мертв, GC убивает владельца). Вместо смены владения: сильные ссылки + done-callback отмена/завершение задач с `unregister`, плюс reaper orphan-сессий по таймауту с force-close. Поведение drain и `force_close_all` не меняется, дефолт 600 с не меняется.

### D9: Idle-таймаут только по полному молчанию, по умолчанию выключен
Почему: thinking-модели и долгие tool-раунды штатно молчат минутами, фиксированный max-idle зарежет дорогие сессии. Таймаут срабатывает только при отсутствии любых кадров дольше max-idle, сбрасывается любым кадром (включая thinking-дельты и tool-start), по умолчанию выключен и включается флагом для staging-калибровки. Поведение без флага не меняется.

### D10: Evict только по terminal-событию плюс LRU-backstop
Почему: голый LRU-256 выкидывает ключи незавершенных ответов (дельты прилетают позже setup-части, miss дает пустой transcript без ошибки). Активные `response_id` защищены от вытеснения, evict идет по `response.done/failed`, LRU-кап работает только как backstop для orphan-ключей.

### D11: Очереди Chirp не блокируются: put_nowait с дропом и пробуждением
Почему: bounded `Queue` с голым `await put` при ушедшем consumer дедлочится навсегда. Продюсер использует `put_nowait`, при полной очереди дропает с счетчиком и пробуждает ждущих при `close()`. Политика дропа — tail-drop (новое), порядок ранее принятых кадров сохранен.

### D12: Pending-буфер: tail-drop с сохранением порядка
Почему: дроп головы вырезает середину аудиопотока без маркера, дроп хвоста неверной реализацией выкидывает свежее. При превышении капа после `unsent + pending` дропается хвост (новые кадры), голова (старые, уже упорядоченные) сохраняется, счетчик дропов в лог. Совпадает с существующим поведением дропа входящих при переполнении.

### D13: Reconnect под локом с generation counter
Почему: два пути (клиентский насос и фоновый retry) собирают `unsent+pending` и флашат в новый сокет дважды, `finally` закрывает сокет, в который пишет второй путь. Забор-и-очистка pending атомарна под локом, опоздавший запрос присоединяется к in-flight попытке по generation counter. Последовательное поведение не меняется.

## Risks / Trade-offs

- [Risk] Дроп старых `messages` обрежет spend-лог длинного звонка → Mitigation: решение D7, spend-критичные не дропаются, паритет spend проверяется дифф-тестом задачи 1.1. Отдельного журнала spend-событий нет, формат spend-записей не меняется.
- [Risk] Сильный реестр продолжит пинить потерянные сессии → Mitigation: решение D8, done-callback плюс reaper orphan-сессий по таймауту с force-close и счетчиком.
- [Risk] Таймаут чтения убьет медленную, но живую сессию → Mitigation: решение D9, таймаут по умолчанию выключен, срабатывает только на полное молчание дольше max-idle, сбрасывается любым кадром.
- [Risk] Evict выкинет ключ активного ответа → Mitigation: решение D10, активные `response_id` защищены, evict по terminal-событию.
- [Risk] Bounded очередь дедлочится при ушедшем consumer → Mitigation: решение D11, `put_nowait` с дропом и пробуждением ждущих при `close()`.
- [Risk] Дроп pending нарушит порядок аудио → Mitigation: решение D12, tail-drop с сохранением порядка головы.
- [Risk] Конкурентный reconnect даст двойную отправку или use-after-close → Mitigation: решение D13, лок плюс generation counter.
- [Risk] Расхождение с `realtime-bridge-v2` (drop vs backpressure, двойные таймауты) → Mitigation: этот чендж только капы поверх текущего кода без writer-очереди; backpressure-пауза чтения остается за `realtime-bridge-v2`, политики задокументированы как временные и совместимые (tail-drop до появления writer).

## Migration Plan

1. Фаза 1: капы накопителей ядра (`messages`, `input_messages`, `tool_calls`, чанки, pending-буфер).
2. Фаза 2: weak-реестр, закрытие сокетов в retry, таймауты чтения и отмены.
3. Фаза 3: evict в адаптерах (xAI, Gemini cap-аудит), границы Chirp, Bedrock `logged` кап.
4. Фаза 4: счетчики и процедура `tracemalloc`, staging-звонок 30+ минут с плоским RSS.
- Rollback каждой фазы: предыдущий коммит, клиентский диалект и схемы spend-записей не меняются.
